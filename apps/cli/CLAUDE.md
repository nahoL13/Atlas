# @atlas/cli

Primeira interface executável do Atlas (SPEC-0003). Casca de processo (`main.ts`) + `run()` testável + sementes de Input/Output Gateway.

- Aplicação: consome `@atlas/core` (`createAtlas`), não reimplementa lógica do Core.
- Sementes de Input Gateway (normaliza `argv`+`env`) e Output Gateway (entrega stdout/stderr) — interfaces locais; promover a `@atlas/contracts` só com um 2º consumidor (via ADR).
- Precedência de config: `flags > env > arquivo > defaults` (ADR-0006); `flags` e `env` implementados; `arquivo` reservado. Validação fica no core.
- Múltiplas raízes de permissão (SPEC-0018): `--allow-read`/`--allow-write` são **flags repetíveis** (`multiple: true` do `parseArgs` → `string[]`); `ATLAS_ALLOW_READ`/`ATLAS_ALLOW_WRITE` aceitam **lista por `path.delimiter`** (`:` POSIX, `;` Windows). Precedência inalterada: a lista da fonte de maior precedência **substitui** por inteiro a inferior (sem merge); segmentos vazios/só-espaço são filtrados (`trim`); fonte que colapsa para lista vazia é tratada como "não fornecida" (cai no default do core). Tudo em `src/gateway/input-gateway.ts` (`resolveRootList`/`filterNonEmpty`); o núcleo já operava sobre listas — a fatia foi só a borda de entrada.
- **Rede (SPEC-0055/ADR-0026):** `--allow-net <host>` é flag repetível, mesmo molde acima; `ATLAS_ALLOW_NET` aceita lista por **vírgula** — **não** `path.delimiter`, porque hostname não é caminho de arquivo (`resolveRootList` generalizada com um parâmetro de separador, reusada pelas três variáveis). Validação de formato de hostname vive no core (`loadConfig`), não aqui. `atlas status` passa a imprimir `netRoots: <lista>` ou `(nenhum)`, no mesmo formato de `writeRoots`; o rótulo cobre só a política de **Tools** — o endpoint do provedor de modelo (`@atlas/model-gateway`) não passa por `netRoots`.
- **Busca na internet (SPEC-0057):** `--search-url <url>` é flag **não repetível** (é um endpoint, não uma lista); `ATLAS_SEARCH_URL` é a variável equivalente; precedência `flag > env`, valor repassado **cru** ao core (validação em `loadConfig`, ADR-0006). Nenhuma das duas fontes ⇒ `override.tools` não é setado (cai no default `''` do core, e `web_search` não é registrada). `atlas status` passa a imprimir `search: <url>` ou `search: (não configurado)`. `HELP_TEXT` documenta a flag/env com a nota de que o host do endpoint também precisa de `--allow-net`.
- **Auto-start de dependências externas (SPEC-0060/SPEC-0061/ADR-0027):** `--auto-start-ollama` é flag booleana **não repetível** (`ATLAS_AUTO_START_OLLAMA` equivalente, coerida por `parseBooleanSetting`); `--auto-start-search-container <nome>` é flag **nominal**, não booleana, também não repetível (`ATLAS_AUTO_START_SEARCH_CONTAINER` equivalente) — o container não tem identidade default, então "se" e "qual" se fundem no mesmo valor. Precedência `flag > env` para as duas; default `false`/`''` (fail-closed). Env fora do conjunto aceito para o Ollama (`1/true/yes/on` × `0/false/no/off`, case-insensitive), ou um nome de container inválido (charset do Docker) ⇒ `CliUsageError` nomeando os valores aceitos. `run.ts` chama `createDependencyManager().ensure(resolveDependencyConfig(...))` **uma única vez por processo**, logo após os desvios de `help`/`version`/`persona` e imediatamente antes de `createAtlas` — a CLI **nunca** chama `release()` para nenhuma das duas (assimetria deliberada com `apps/desktop`, ADR-0027(e)). Avisos de `'started'`/`'failed'` saem em **stderr** com textos pinados, um bloco por dependência; `'disabled'`/`'already-running'` são silenciosos; nenhum desfecho altera o código de saída do comando. `atlas status` ganha as linhas `ollama auto-start: …` e `search container auto-start: …` (quatro textos pinados e exaustivos cada, selecionadas por busca do `dependency` no relatório, nunca por índice fixo). **Custo assumido:** com os dois opt-ins ligados e ambas as dependências fora do ar, comandos que nunca tocam o Model Gateway (`memory list`/`forget`/`skills list`/`status`) pagam até ~17 s de bloqueio antes de imprimir qualquer coisa (10 s do Ollama + 5 s do container + health-checks, tratamento sequencial) — consequência direta do disparo único no bootstrap (ADR-0027(d)); só `help`/`version`/`persona` escapam. Com a SPEC-0061, o ADR-0027 fica inteiramente consumido — detalhe da extensão Docker em `packages/core/CLAUDE.md`.
- Execução sem `dist/`: roda o fonte `.ts` via `tsx` (ADR-0005); `bin` → `./src/main.ts` com shebang `#!/usr/bin/env -S npx tsx`. Dev: `tsx src/main.ts` ou `pnpm run atlas`.
- Sem dependências de _runtime_ além de `@atlas/contracts` e `@atlas/core`; `tsx` é _dev tooling_. Parsing via `node:util`.
- **Aprendizado (SPEC-0020)**: `atlas ask` e `atlas chat` iteram `result.learned`/`turn.learned` (candidatos propostos pelo Cognitive), gravam cada um via `atlas.memory.remember(texto, 'learned')` e imprimem o traço `💡 lembrado: <fato>` (`renderLearned` em `src/gateway/steps-trace.ts`). `atlas memory list` exibe a origem de cada fato (`origem: user|learned`; sem `source` → `user`); `atlas remember` segue gravando `'user'` (default). A mediação é da borda (padrão ADR-0009): o Cognitive propõe, a Memory grava.
- **Deduplicação determinística (SPEC-0022)**: `atlas.memory.remember(...)` retorna `{ fact, created }` (mudança não-aditiva do contrato). `ask.ts`/`chat.ts` só chamam `renderLearned` quando `created` for `true` — um fato aprendido já conhecido não gera ruído de "lembrado" a cada turno. `remember.ts` (`atlas remember <texto>`) distingue: `created` → `"Lembrado [id]: texto"`; `!created` → `"Já conhecido [id]: texto"`.
- **Consolidação do acervo legado (SPEC-0023)**: novo subcomando `atlas memory dedupe [--apply]` (irmão de `memory list`, mesmo guarda-chuva). `src/gateway/input-gateway.ts` reconhece o subcomando `dedupe` (subcomando desconhecido segue erro de uso, agora listando `list`/`dedupe`) e a flag booleana `--apply`. `src/commands/memory.ts` ganha `runMemoryDedupe(atlas, apply, output)`: chama `atlas.memory.dedupe({ apply })` e só renderiza o `DedupeReport` — sem grupos, "Nenhuma duplicata encontrada."; com grupos e dry-run, lista cada sobrevivente e as duplicatas que **seriam** removidas + dica de rodar com `--apply`; com grupos e `applied`, confirma o que **foi** removido. `run.ts` despacha `memory dedupe` para `runMemoryDedupe` (`memory list` segue em `runMemoryList`); `HELP_TEXT` ganhou a linha `memory dedupe [--apply]`. A CLI não reimplementa normalização nem toca o storage — só invoca e renderiza (autoridade da Memory, Artigo 11).
- **Categorias de conhecimento (SPEC-0029)**: `atlas remember "<texto>" --category <fact|episode|project> [--subject <projeto>]` repassa a categoria/projeto a `atlas.memory.remember`; `atlas memory list [--category <c>]` filtra e exibe categoria (e projeto, quando houver) de cada registro. `src/gateway/input-gateway.ts` valida uso — `--category` desconhecido, `project` sem `--subject`, `--subject` em branco (`''`/`"   "`) ou combinado com categoria diferente de `project` são todos `CliUsageError` — mas a **garantia** (invariante do modelo persistido) é do `@atlas/memory`, a CLI só antecipa a mensagem amigável. `HELP_TEXT` documenta as duas flags.
- `atlas chat` (SPEC-0014): cada turno passa por `cognitive.respond`, que agora pode planejar e executar Tools. O traço de `steps` é impresso a cada turno reusando `renderSteps` (`src/gateway/steps-trace.ts`), compartilhado com `atlas ask`. O `ConfirmPort` de ações destrutivas (`delete_file`) é construído sobre o **mesmo** `LineReader` da sessão (`src/gateway/confirm-port.ts`, `createLineReaderConfirmPort`) e injetado em `createAtlas(..., { confirm })` — nunca um segundo `readline` sobre `stdin`. Em `run.ts`, o `LineReader` do `chat` nasce **antes** de `createAtlas` justamente para viabilizar essa composição.
- **Skills (SPEC-0025)**: `atlas skills list` mostra o catálogo (`id`/nome/`scope`/ativo-inativo/versão) via `atlas.skills.list()`. `atlas skills build "<capacidade>"` chama `atlas.skillBuilder.build({ capability })` e imprime a Skill produzida em sucesso, ou as pendências (`issues`) em falha — nunca lança. Parsing do subcomando (`list`/`build` + a `capability` como positional) em `src/gateway/input-gateway.ts` (`skillsSubcommand`/`capability`); despacho em `run.ts` (`runSkillsList`/`runSkillsBuild`, `src/commands/skills.ts`); `HELP_TEXT` cobre os dois subcomandos. A CLI só invoca e renderiza — nenhuma lógica de validação/parsing de `SkillDraft` mora aqui (autoridade do Builder).
- **CRUD de Persona custom pelo terminal (SPEC-0044, equivalente CLI da SPEC-0039/GUI)**: `atlas persona list|show <id>|create "<nome>" [flags]|edit <id> [flags]|delete <id> [--yes]`. Sobre **o mesmo arquivo** que `apps/desktop` usa — o caminho é derivado **uma única vez** pela função canônica `personaStoragePath(resolveDataDir(...))` de `@atlas/core` (`src/gateway/persona-composition.ts`, `createCliPersonaStorage`/`createCliPersonaService`), nunca um `join` reinventado; uma Persona criada no terminal aparece na janela e vice-versa, sem tradução. `createCliPersonaService` compõe `createPersonaService({ storage })` diretamente no app — a **única** exceção delimitada de composição direta de um serviço da plataforma em `apps/cli` (mesma reusada por `apps/desktop` desde a SPEC-0039/D12; `packages/core/CLAUDE.md` documenta a fronteira). **Nunca** aciona `loadConfig`: achar o arquivo independe de a Persona ativa ser válida.
  - **`run.ts` desvia os subcomandos de `persona` ANTES de `createAtlas`** (nunca sobe o Core, nunca compõe Runtime/Tools/Memory/gateway de modelo): evita o deadlock circular em que um `ATLAS_PERSONA` órfão impediria listar/recriar Personas pela própria CLI.
  - **Todo comando restante (`status`/`ask`/`chat`/`remember`/`forget`/`memory`/`skills`) passa a injetar `personaStorage: createCliPersonaStorage(...)` em `createAtlas`**, para que `--persona <id-custom>`/`ATLAS_PERSONA` resolvam Personas custom em qualquer comando. **Custo assumido**: o arranque de todo comando passa a ler o arquivo de Personas (Persona Service é composto antes do `loadConfig`, `packages/core/src/index.ts`) — um arquivo corrompido (`PersonaError`/`AtlasError` code `ATLAS_PERSONA`) derruba `status`/`ask`/`chat` também, não só `atlas persona`. Mitigação: mensagem amigável citando o **caminho do arquivo** + a **saída de emergência** (corrigir/remover o arquivo, ou apontar outro `--data-dir`/`ATLAS_DATA_DIR`) — nunca stack trace crua, nunca reescrita silenciosa.
  - **"Embutida" é sempre derivada**, nunca lida de um campo `Persona.builtin` (que não existe): `PERSONA_IDS.includes(id)` sobre os ids de `PersonaService.list()` — mesmo mecanismo de `apps/desktop/src/core-bridge.ts`. `jarvis`/`neutral` seguem imutáveis e somente-leitura também pela CLI.
  - **`edit` é patch, `create` preenche o resto com `''`**: editar só sobrepõe os campos informados (lê a Persona atual e preserva o resto, inclusive `voiceURI`); criar exige só o nome (positional) e materializa os demais campos textuais como `''`/`communicationRules: []` (paridade com a `neutral` embutida). `--rule` é repetível e **substitui** a lista inteira (nunca merge); `--rule ""` isolado produz `communicationRules: []` (chave presente = limpar, distinto de "não informado"). `--voice-uri ""` remove a propriedade `voiceURI` de uma Persona editada.
  - **`--voice-uri` é string opaca na CLI**: aceita `piper:<id>` ou o `voiceURI` de uma voz do SO, sem validar, sem catálogo e sem reproduzir áudio — nenhum comando da CLI fala. Na janela do desktop, sob a política Piper-only (SPEC-0041), uma voz do SO vinculada por aqui não é honrada enquanto Piper estiver disponível; sem Piper disponível, a janela volta a usar vozes do SO normalmente (SPEC-0043, ADR-0020(b) restaurado no caminho `'os'`).
  - **`persona delete` exige consentimento explícito, fail-closed** (mesmo molde do `LineReader`/`ConfirmPort` do `chat`, SPEC-0014): prompt `[s/N]` por padrão, `--yes` pula a pergunta em uso não interativo; sem leitor, EOF, ou resposta diferente de `s`/`sim` não apagam nada e retornam código **1** com "Remoção cancelada; nada foi apagado." Ordem obrigatória: validar (id existe + não é embutida) → perguntar → efeito — o leitor nunca é consultado para um id inexistente/embutido. Avisa (não recusa) quando o id coincide com o valor cru de `configOverride.persona` — sem marcar a Persona ativa em `persona list` (exigiria `loadConfig`, reabrindo o deadlock). Não há `atlas persona use <id>` (seleção durável): a escolha continua por `--persona <id>`/`ATLAS_PERSONA`.
  - `src/commands/persona.ts` só orquestra/renderiza (`PersonaService` injetado, testável com fake em memória); toda validação semântica (slug, colisão, campos obrigatórios) é autoridade de `@atlas/persona`.
