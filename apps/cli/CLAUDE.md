# @atlas/cli

Primeira interface executável do Atlas (SPEC-0003). Casca de processo (`main.ts`) + `run()` testável + sementes de Input/Output Gateway.

- Aplicação: consome `@atlas/core` (`createAtlas`), não reimplementa lógica do Core.
- Sementes de Input Gateway (normaliza `argv`+`env`) e Output Gateway (entrega stdout/stderr) — interfaces locais; promover a `@atlas/contracts` só com um 2º consumidor (via ADR).
- Precedência de config: `flags > env > arquivo > defaults` (ADR-0006); `flags` e `env` implementados; `arquivo` reservado. Validação fica no core.
- Múltiplas raízes de permissão (SPEC-0018): `--allow-read`/`--allow-write` são **flags repetíveis** (`multiple: true` do `parseArgs` → `string[]`); `ATLAS_ALLOW_READ`/`ATLAS_ALLOW_WRITE` aceitam **lista por `path.delimiter`** (`:` POSIX, `;` Windows). Precedência inalterada: a lista da fonte de maior precedência **substitui** por inteiro a inferior (sem merge); segmentos vazios/só-espaço são filtrados (`trim`); fonte que colapsa para lista vazia é tratada como "não fornecida" (cai no default do core). Tudo em `src/gateway/input-gateway.ts` (`resolveRootList`/`filterNonEmpty`); o núcleo já operava sobre listas — a fatia foi só a borda de entrada.
- Execução sem `dist/`: roda o fonte `.ts` via `tsx` (ADR-0005); `bin` → `./src/main.ts` com shebang `#!/usr/bin/env -S npx tsx`. Dev: `tsx src/main.ts` ou `pnpm run atlas`.
- Sem dependências de _runtime_ além de `@atlas/contracts` e `@atlas/core`; `tsx` é _dev tooling_. Parsing via `node:util`.
- **Aprendizado (SPEC-0020)**: `atlas ask` e `atlas chat` iteram `result.learned`/`turn.learned` (candidatos propostos pelo Cognitive), gravam cada um via `atlas.memory.remember(texto, 'learned')` e imprimem o traço `💡 lembrado: <fato>` (`renderLearned` em `src/gateway/steps-trace.ts`). `atlas memory list` exibe a origem de cada fato (`origem: user|learned`; sem `source` → `user`); `atlas remember` segue gravando `'user'` (default). A mediação é da borda (padrão ADR-0009): o Cognitive propõe, a Memory grava.
- **Deduplicação determinística (SPEC-0022)**: `atlas.memory.remember(...)` retorna `{ fact, created }` (mudança não-aditiva do contrato). `ask.ts`/`chat.ts` só chamam `renderLearned` quando `created` for `true` — um fato aprendido já conhecido não gera ruído de "lembrado" a cada turno. `remember.ts` (`atlas remember <texto>`) distingue: `created` → `"Lembrado [id]: texto"`; `!created` → `"Já conhecido [id]: texto"`.
- **Consolidação do acervo legado (SPEC-0023)**: novo subcomando `atlas memory dedupe [--apply]` (irmão de `memory list`, mesmo guarda-chuva). `src/gateway/input-gateway.ts` reconhece o subcomando `dedupe` (subcomando desconhecido segue erro de uso, agora listando `list`/`dedupe`) e a flag booleana `--apply`. `src/commands/memory.ts` ganha `runMemoryDedupe(atlas, apply, output)`: chama `atlas.memory.dedupe({ apply })` e só renderiza o `DedupeReport` — sem grupos, "Nenhuma duplicata encontrada."; com grupos e dry-run, lista cada sobrevivente e as duplicatas que **seriam** removidas + dica de rodar com `--apply`; com grupos e `applied`, confirma o que **foi** removido. `run.ts` despacha `memory dedupe` para `runMemoryDedupe` (`memory list` segue em `runMemoryList`); `HELP_TEXT` ganhou a linha `memory dedupe [--apply]`. A CLI não reimplementa normalização nem toca o storage — só invoca e renderiza (autoridade da Memory, Artigo 11).
- `atlas chat` (SPEC-0014): cada turno passa por `cognitive.respond`, que agora pode planejar e executar Tools. O traço de `steps` é impresso a cada turno reusando `renderSteps` (`src/gateway/steps-trace.ts`), compartilhado com `atlas ask`. O `ConfirmPort` de ações destrutivas (`delete_file`) é construído sobre o **mesmo** `LineReader` da sessão (`src/gateway/confirm-port.ts`, `createLineReaderConfirmPort`) e injetado em `createAtlas(..., { confirm })` — nunca um segundo `readline` sobre `stdin`. Em `run.ts`, o `LineReader` do `chat` nasce **antes** de `createAtlas` justamente para viabilizar essa composição.
- **Skills (SPEC-0025)**: `atlas skills list` mostra o catálogo (`id`/nome/`scope`/ativo-inativo/versão) via `atlas.skills.list()`. `atlas skills build "<capacidade>"` chama `atlas.skillBuilder.build({ capability })` e imprime a Skill produzida em sucesso, ou as pendências (`issues`) em falha — nunca lança. Parsing do subcomando (`list`/`build` + a `capability` como positional) em `src/gateway/input-gateway.ts` (`skillsSubcommand`/`capability`); despacho em `run.ts` (`runSkillsList`/`runSkillsBuild`, `src/commands/skills.ts`); `HELP_TEXT` cobre os dois subcomandos. A CLI só invoca e renderiza — nenhuma lógica de validação/parsing de `SkillDraft` mora aqui (autoridade do Builder).
