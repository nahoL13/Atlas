# @atlas/skills

Skill Registry + Skill Builder (Extension) — catálogo passivo em memória e construtor de Skills (ADR-0017/SPEC-0025).

- `createSkillRegistry({ skills? })` → `SkillRegistry` (síncrono, sem IO), no molde de `createToolRegistry` (SPEC-0010): `register`/`get`/`deactivate`/`remove`/`list`. `get` unifica "localizar" e "carregar" — num catálogo em memória não há carga preguiçosa a distinguir; a separação volta quando Skills forem persistidas (fatia futura). `register` faz upsert por `id`, mas **rejeita** (`SkillError`, `ATLAS_SKILL`) qualquer registro que envolva uma Skill `permanent` já registrada por aquele `id` — seja substituindo uma `permanent` existente por uma `temporary`, seja tentando registrar uma `permanent` sobre um `id` `temporary` já existente. Só um upsert entre duas Skills de mesmo `scope` (nenhuma das duas `permanent`) é aceito. Sem persistência: o Registry vive só no processo.
- `createSkillBuilder({ gateway, registry, tools })` → `SkillBuilder` — `build(request)` percorre os 8 passos do Module Catalog. A **única** chamada `gateway.generate` (passo 5) produz um `SkillDraft` estruturado em JSON (`name`/`description`/`instructions`/`toolIds`, todos derivados do modelo); o Builder **parseia** essa saída no molde do learner (ADR-0016/`@atlas/cognitive`) — JSON malformado/incompleto vira `issues`, nunca lança. Validação estática (passos 6-7): contrato bem-formado (campos presentes; `name`/`instructions` não vazios após `trim`; `toolIds` array de strings) **e** todo `toolId` resolve em `tools` (o `ToolRegistry` injetado). Em sucesso (passo 8), completa **deterministicamente** `id` (namespace `tmp-…`, via `crypto.randomUUID()`), `version` (`'1.0.0'`) e `scope: 'temporary'` — nunca do modelo, mesmo que o JSON tente injetar esses campos (são ignorados) — e registra via `registry.register`. Em falha, devolve `{ ok: false, issues }` sem registrar. **Nunca** promove `temporary`→`permanent`.
- `BUILTIN_SKILLS`: seed(s) permanente(s), dado inerte, para o Registry não nascer vazio (ao menos 1). Ids fora do namespace `tmp-` reservado ao Builder.
- Erro estruturado: `SkillError` (`AtlasError`, `code: 'ATLAS_SKILL'`).
- Contratos (`Skill`/`SkillScope`/`SkillDescriptor`/`SkillDraft`/`SkillRegistry`/`SkillBuilder`/`SkillBuildRequest`/`SkillBuildResult`) vivem em `@atlas/contracts` — o Registry é módulo catalogado como consumido por Planner/Runtime (Module Catalog), mesmo critério de `Tool`/`Plan` (ADR-0012), ainda que **nada consuma Skills nesta fatia**.
- **Registry consumido pelo Planner desde a SPEC-0026 (ADR-0018), superando parcialmente o ADR-0017:** o Planner passa a **selecionar automaticamente** no máximo uma Skill por turno (nunca o usuário — sem flag/config de Skill ativa) e o Cognitive Core injeta suas `instructions` na composição da resposta; o Runtime segue **sem** conhecer Skills (não escolhe, não recebe `skills`, não filtra Tools por `toolIds`). `@atlas/skills` continua sem ser importado por Planner/Cognitive/Runtime — o consumo lê o catálogo por uma projeção somente-leitura (`SkillCatalogPort`, tipo interno a `@atlas/cognitive`) fiada por `@atlas/core`. Só as Skills **registradas no processo** (na prática, as `permanent` semeadas) são consumíveis; Skills `temporary` construídas pelo Builder ainda **não** sobrevivem entre invocações — persistência segue fatia futura.
- Depende só de `@atlas/contracts`; só `@atlas/core` importa suas implementações (Regra 11/ADR-0004). Uma Skill **não** tem canal com o usuário (Module Catalog, regra 4) — nenhum campo/método de fala.
