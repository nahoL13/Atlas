# @atlas/core

Composition root da plataforma (ADR-0003) + Configuration Service + Lifecycle Manager.

- Único package autorizado a importar implementações de outros packages, exclusivamente para composição (Regra de Dependência 11).
- Não deve conter lógica de domínio — apenas wiring, ciclo de vida e configuração.
- Composição manual por factory functions (ADR-0004): dependências explícitas por parâmetro; sem container de DI.
- Estados de lifecycle e config são contrato público: mudanças exigem atualizar `@atlas/contracts` e verificar consumidores.
- Compõe `nodeReadlineConfirmPort()` como `ConfirmPort` default do Runtime (`@atlas/runtime`); `CreateAtlasDeps.confirm?` permite injetar um fake nos testes (sem terminal real). Registra `delete_file`/`mkdir`/`append_file` no `ToolRegistry` ao lado de `write_file` (SPEC-0013).
- **Fecho atômico de TOCTOU (SPEC-0017):** `createAtlas` cria `permissions` **antes** das portas de FS default, e fia `permissions.isContained.bind(permissions)` como o `verify` injetado em `nodeFsReadPort({ verify })`/`nodeFsWritePort({ verify })` — as Tools de FS registradas (`read_file`/`write_file`/`append_file`) passam a operar com o fecho atômico ativo (O_NOFOLLOW + ancoragem de identidade do fd + veredicto de contenção no instante do uso). `CreateAtlasDeps.fsRead?`/`fsWrite?` seguem injetáveis nos testes (bypassam `nodeFsReadPort`/`nodeFsWritePort` por completo, então não exercitam essa fiação). **SPEC-0024** inverteu o *default* de `verify` em `@atlas/tools` para fail-closed (`() => false`) — sem efeito aqui: `createAtlas` já fiava `verify` real desde a SPEC-0017, então o comportamento em produção não muda; `packages/core/src` permanece intocado por essa SPEC.
- **Provider de memória recomposto ao vivo (SPEC-0021, ADR-0011):** `createAtlas` fia `memoryPrompt: () => memory.prompt()` no `createCognitiveCore` — provider síncrono **sempre definido** que delega à Memory (autoridade exclusiva do estado persistente, Artigo 11). Substitui o `const memoryPrompt = memory.prompt()` estático de antes e o spread condicional (`...(memoryPrompt !== undefined ? { memoryPrompt } : {})`); como o provider é sempre definido, a atribuição é direta e o `exactOptionalPropertyTypes` fica satisfeito. É o Cognitive que amostra o provider 1x por turno; a Memory apenas produz o texto. Nenhuma mudança em `apps/cli` — o laço de aprendizado fecha dentro da própria sessão. **Desde a SPEC-0030**, o provider ganhou argumentos e virou `memoryPrompt: (query, limit) => memory.prompt({ query, limit })` — `@atlas/core` só repassa a consulta e o orçamento (`MEMORY_RECALL_LIMIT`, embutido em `@atlas/cognitive`); nenhuma política nova no composition root.
- **Skill Registry + Skill Builder (SPEC-0025, ADR-0017):** `createAtlas` cria `skills = createSkillRegistry({ skills: BUILTIN_SKILLS })` e `skillBuilder = createSkillBuilder({ gateway, registry: skills, tools: registry })` — fiado com o **mesmo** `gateway`/`ToolRegistry` já compostos para o resto da plataforma, sem nova porta injetável. Expostos como `atlas.skills`/`atlas.skillBuilder`.
- **Consumo de Skills pelo Planner (SPEC-0026, ADR-0018):** `createAtlas` fia `skillCatalog: { list: () => skills.list(), get: (id) => skills.get(id) }` em `createCognitiveCore` — projeção **somente-leitura** do `SkillRegistry` (menor privilégio: o Cognitive nunca `register`/`deactivate`/`remove`), no molde do `memoryPrompt` acima. `createRuntime` **não** recebe `skills` — o consumo é só no Planner/Cognitive Core, o Runtime segue agnóstico a Skills.
- **Re-export de catálogo de Personas (SPEC-0037, Decisão D4):** `packages/core/src/index.ts` re-exporta `createPersonaService`/`PERSONA_IDS` de `@atlas/persona`, ao lado de `loadConfig`/`defaultConfig`/`createLifecycle` — **aditivo, sem wiring, sem lógica nova**, `createAtlas` inalterado. É a porta pela qual `apps/*` leem o catálogo de Personas (para exibir/validar escolha do usuário — ex.: o seletor de Persona do `apps/desktop`) continuando a importar implementação **só** de `@atlas/core` (ADR-0003 / Regra de Dependência 11 do Project Structure): a alternativa "app depende de `@atlas/persona` direto" instanciaria um **segundo** `PersonaService` fora do composition root (o `createAtlas` já cria o seu) e está rejeitada pelo próprio ADR-0003.
- **Fronteira do re-export, alargada de forma delimitada pela SPEC-0039 (Decisão D12).** Até a SPEC-0038, a fronteira era estrita: "leitura de catálogo/config **inerte**"; proibido, sem ADR, o app "instanciar um serviço da plataforma para injetá-lo em outro componente, ou montar/substituir wiring que hoje vive em `createAtlas`". O ADR-0020 (Persona persistível com storage injetável) desenhou deliberadamente `PersonaStorage`/`createFilePersonaStorage` para serem **injetados por quem compõe** — sem default dentro de `createAtlas`, para não regredir `apps/cli` (D3 da SPEC-0039). Isso exige, por construção, que **algum** composition root monte `createPersonaService({ storage })` fora de `createAtlas` sempre que precisar de CRUD sem subir o Core inteiro (`apps/desktop/src/core-bridge.ts`, funções de Persona). A fronteira nova, explícita:
  - **Permitido**, só para este caso desenhado pelo próprio ADR-0020: compor `createPersonaService({ storage })` sobre `createFilePersonaStorage(path)` (ambos re-exportados aqui), e injetar essa mesma porta em `createAtlas` pelo `deps.personaStorage?` público — para que o Core e a composição paralela nunca apontem para storages diferentes.
  - **Continua proibido, sem ADR:** compor qualquer **outro** serviço da plataforma no app (Memory, Context, Permissions, Runtime...), substituir wiring interno de `createAtlas`, ou compor um segundo Core. Qualquer necessidade além disso é sinal de ADR, não de mais re-exports.
- **`resolveDataDir(override?: AtlasConfigOverride): string`** (`packages/core/src/config/data-dir.ts`, SPEC-0039, Decisão D17) — via oficial para resolver **só** o `dataDir`, pela mesma precedência de `loadConfig` (`flags > env > defaults`; slot `arquivo` do ADR-0006 não implementado), **sem nunca validar o campo `persona`** (não aciona `PERSONA_IDS`). Pura, sem IO. Existe porque achar **onde** um arquivo guardado sob `dataDir` está (ex.: `personas.json`) precisa ser possível **antes** de — e independentemente de — saber se a Persona ativa é válida; resolver as duas coisas pela mesma via (`loadConfig`) cria um ciclo (ver SPEC-0039 Decisão D17: correção do bloqueante B1). `loadConfig` consome a mesma precedência internamente (helpers não exportados do package) — nunca duas implementações de "qual é o `dataDir` efetivo" no repositório.
- **`personaStoragePath(dataDir: string): string`** (`packages/core/src/index.ts`, SPEC-0039) — função pura, sem IO, `join(dataDir, 'personas.json')`. **Único** lugar do repositório onde esse caminho é derivado; `apps/desktop` o consome sempre com o `dataDir` já resolvido por `resolveDataDir(...)` daquela mesma chamada (nunca por conta própria) — para que uma futura fatia de CLI encontre o **mesmo** arquivo, em vez de reinventar o `join` e tornar as Personas invisíveis entre interfaces.
- **Portão de rede (SPEC-0055/ADR-0026):** `defaults.permissions.netRoots: []`; `loadConfig` faz merge (`override.permissions?.netRoots ?? defaults...`) e **valida** cada hostname (string não vazia, sem espaço, sem `://`/`/`/`@`/`:`/`?`/`#`) — a CLI repassa cru, a validação de formato vive aqui (ADR-0006). `createPermissionService(...)` passa a receber `netRoots: config.permissions.netRoots`. `CreateAtlasDeps.http?: HttpPort` segue o mesmo molde de `git?`/`fsRead?` (default `nodeHttpPort()`); `createAtlas` registra `http_get` (`@atlas/tools`) no `ToolRegistry`. Nenhuma outra mudança de wiring.
- **`project_info` registrada (SPEC-0056):** `createAtlas` registra `createProjectInfoTool({ fs: fsRead, git })` no `ToolRegistry`, reusando as **mesmas** instâncias `fsRead`/`git` já compostas para as demais Tools de FS/git — nenhuma porta, config, dep ou campo novo em `CreateAtlasDeps`.
- **Auto-start de dependências externas (SPEC-0060/SPEC-0061/ADR-0027):** `createDependencyManager({ process?, sleep? }) → { ensure(config), release() }` (`packages/core/src/dependencies/dependency-manager.ts`) + `ProcessPort` — unidade **nova e independente** do `Lifecycle` de `createAtlas` (que sai sem uma linha alterada; `packages/core/src/index.ts` só exporta a fábrica). Cobre hoje **duas** dependências, cada uma com operações nomeadas e fixas, nunca `run(command, args)` genérico:
  - **Ollama** (SPEC-0060): `isOllamaRunning`/`startOllama`/`stopOllama`. Adaptador real `nodeProcessPort()` (health-check `GET <baseUrl>/api/tags`, timeout 2 s, só `response.ok` conta; start via `spawn('ollama', ['serve'], { detached: true, stdio: 'ignore' })` + `unref()`; stop via `SIGTERM` → 2 s → `SIGKILL`; polling de prontidão 40 × 250 ms). `ollamaBaseUrl` só herda `model.baseUrl` quando o provider efetivo é `'local'` (igualdade exata) — evita sondar sem credencial um host `remote`/`fake` de terceiro.
  - **Container de busca** (SPEC-0061, Docker): `inspectSearchContainer`/`startSearchContainer`/`stopSearchContainer` — nunca `run`/`create`/`pull`/`rm`/`kill`/`compose` (ADR-0027(h)). Adaptador real invoca `docker inspect --type container --format '{{.State.Running}}' <nome>` (`--type container` evita a resolução por tipo automático do `inspect` casar com uma imagem homônima), `docker start <nome>`, `docker stop <nome>`; polling de prontidão 20 × 250 ms (5 s) sobre o `inspect`, não sobre a saúde HTTP do serviço. `stop` deriva da cláusula (e) (desligamento simétrico), não de (h).
  - Posse de **cada** processo/container é registrada no **sucesso do `spawn`/`start`**, nunca na prontidão do polling — um daemon/container lento nunca fica órfão ao fechar a janela; posse vive em campos privados do manager, o adaptador guarda só o *handle*/nome. `DependencyReport.outcomes` carrega **sempre exatamente dois** elementos, ordem pinada `['ollama', 'search-container']`, tratados sequencialmente e de forma independente (a falha de um nunca impede o outro) — `runEnsure` compõe um `DependencyOutcome` por dependência em vez de *early return* por `DependencyReport` inteiro.
  - `resolveDependencyConfig`/`parseBooleanSetting` (`packages/core/src/config/dependency-config.ts`, molde de `resolveDataDir`) resolvem `AtlasConfig.dependencies.autoStartOllama` (booleano, default `false`) e `autoStartSearchContainer` (string, default `''` = desligado, nome do container quando ligado) sem subir o Core e sem validar `persona`; normalização única (`trim` → `isValidContainerName`, charset do Docker) compartilhada com `loadConfig`, para que os dois pontos nunca divirjam sobre o mesmo valor.
  - Health-check fora de `evaluate`/`netRoots` para as duas dependências (ADR-0027(a), nenhuma é Tool); ligar o container **não** concede `netRoots` ao host do endpoint de busca (ADR-0026 intacto). `apps/cli` e `apps/desktop` criam cada um a sua instância de `DependencyManager` no próprio ponto de entrada/saída (`@atlas/core` nunca instancia); nenhum ADR/cláusula do ADR-0013/ADR-0026 é tocado. Com a SPEC-0061, o ADR-0027 fica **inteiramente consumido** — as três SPECs candidatas que ele nomeava (SPEC-0059/0060/0061) estão todas entregues.
- **`ensureSearchContainer` sob demanda, posse como conjunto (SPEC-0062, extensão aditiva):** `DependencyManager` ganha um 3º método, ao lado de `ensure`/`release` (assinaturas dos dois intactas): `ensureSearchContainer(container: string): Promise<DependencyOutcome>` — liga **um** container Docker já nomeado, fora do `ensure` de bootstrap, delegando ao **mesmo** caminho privado (`inspectSearchContainer`→`startSearchContainer`→polling) que o `ensure` já usava (nenhuma lógica duplicada); `container === ''` ⇒ `'disabled'` sem tocar a porta; nunca lança; nunca toca o caminho do Ollama. Memoizado por nome num `Map<string, Promise<DependencyOutcome>>` compartilhado entre `ensure` e `ensureSearchContainer`: duas chamadas concorrentes para o mesmo nome dividem a mesma tentativa; desfecho `'started'`/`'already-running'` permanece na memoização (chamada seguinte não toca a porta); desfecho `'failed'` é removido (chamada seguinte tenta de novo). `ownedContainer: string | undefined` virou `ownedContainers: Set<string>` — a sessão pode ligar mais de um nome, `release()` desliga **cada** um com captura própria (a falha de um nunca impede o outro nem `stopOllama`), e trocar de nome nunca derruba o anterior. `release()` agora **drena** o trabalho em voo (`Promise.allSettled` sobre o `pending` do `ensure` e as tentativas de container ainda não assentadas) **antes** de ler a posse — sem essa ordem, um `ensureSearchContainer` ainda em polling no instante do `release()` registraria posse num conjunto já limpo (correção do bloqueante da 1ª revisão do `architecture-reviewer`); `release()` segue nunca lançando e idempotente. `createAtlas`/`createLifecycle` saem sem uma linha alterada (ADR-0027(d)); consumido só por `apps/desktop` (o gesto do painel de rede/busca, SPEC-0059) — `apps/cli` só ganha o membro novo no fake tipado do teste, sem uso real (D-A1 da SPEC).
- **Inspeção do Ollama + instalação assistida de modelo (SPEC-0063, ADR-0029):** `ProcessPort.isOllamaRunning` foi **substituída** por `inspectOllama(baseUrl): Promise<OllamaInspection>` — a **mesma** requisição `GET <baseUrl>/api/tags` (timeout 2 s, só `response.ok` conta), agora lendo o corpo em vez de descartá-lo: `{ running: false }` sem mudança; `{ running: true, models }` com os `name` válidos do array `models`, na ordem do corpo; `{ running: true, models: undefined }` quando o corpo é ilegível ("de pé, presença de modelo desconhecida"). Todo ponto que chamava `isOllamaRunning` (health-check e polling de prontidão do `ensure`) passou a chamar `inspectOllama` e derivar `running`, **sem nenhuma outra mudança de comportamento** (mesmos orçamentos, mesmos desfechos de `DependencyOutcome`, mesma regra de posse). `DependencyOutcome` ganha `models?: readonly string[]`, aditivo e **estrutural** só nas variantes `'ollama'`/`'already-running'` e `'ollama'`/`'started'` (ausência nas variantes `'disabled'`/`'failed'` provada por `@ts-expect-error`, não por disciplina de escrita) — vem da **mesma** inspeção que já decidiu o desfecho, nunca uma requisição nova; `DependencyReport` sai **sem campo novo** no topo. `DependencyManager` ganha duas operações nomeadas e fixas a mais (ADR-0027(b) confirmada — nenhum `run(command, args)` genérico, e categoria de recurso distinta do `pull`/`create`/`run` de container proibido pelo ADR-0027(h), ver ADR-0029(c)): `pullOllamaModel({ baseUrl, model, onProgress? }): Promise<ModelPullOutcome>` — valida o **formato** do nome contra um regex pinado antes de tocar a porta (`'invalid-model'` sem requisição), recusa um 2º download concorrente sem abortar o corrente (`'busy'`), delega a `ProcessPort.pullOllamaModel` (`POST <baseUrl>/api/pull`, corpo `{ name, stream: true }`, stream NDJSON só de `completed`/`total`/`status === 'success'`/`error` — **nenhum texto do provedor cruza a porta**, D10), e nunca memoiza (dois downloads sequenciais do mesmo nome disparam duas requisições); e `cancelOllamaModelPull(): boolean` — síncrona, aborta via `AbortController` guardado pelo manager (a porta só honra o `signal`), molde de `cancelInFlightOperation` (SPEC-0051). `release()` passa a abortar um download em voo **antes** de drenar o trabalho já existente (posse de container/processo) — sem isso, o `before-quit` esperaria um download de vários GB; não há posse a desfazer sobre um modelo baixado. `packages/core/src/index.ts` exporta os tipos novos (`OllamaInspection`, `ModelPullOutcome`, `ModelPullFailureReason`, `ModelPullProgress`); `createAtlas`/`createLifecycle` saem sem uma linha alterada (ADR-0027(d)). Consumido só por `apps/desktop` (catálogo curado e fixo, painel `Sistema`); `apps/cli` só ganha os membros novos no fake tipado de teste (precedente D-A1 da SPEC-0062).
- **`web_search` registrada condicionalmente (SPEC-0057):** `defaults.tools = { searchUrl: '' }`; `loadConfig` faz merge e **valida** um `searchUrl` não vazio (`new URL`, esquema `http:`/`https:`, sem credenciais embutidas, sem query string/fragmento). `CreateAtlasDeps` ganha `search?: SearchPort` (molde de `http?`/`git?`). Registro **condicional**: só quando `config.tools.searchUrl !== ''`, `createAtlas` chama `deps.search ?? searxngSearchPort({ baseUrl: config.tools.searchUrl })` e registra `createWebSearchTool({ search })` — **sem** endpoint configurado, a Tool simplesmente não existe no `ToolRegistry` daquele processo (mesmo critério de `PiperTts.isAvailable()` da SPEC-0041: ausência de **provedor**, não de **política**). `packages/core/src/index.ts` **não** importa `nodeHttpPort` nem menciona `bodyLimitBytes` para este caminho — o teto de corpo da busca (256 KiB) é decidido só dentro de `searxngSearchPort` (D24 da SPEC). Nenhuma outra mudança de wiring.
