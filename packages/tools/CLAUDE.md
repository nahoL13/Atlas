# @atlas/tools

Tools (Execution/Extension) — adaptadores e catálogo de ferramentas do Atlas (ADR-0012/0013).

- `createToolRegistry()` → `register/get/has/list` sobre um `Map` (fonte do catálogo consumido pelo Runtime).
- `createClockTool({ now? })` → Tool `clock` (data/hora ISO; `now` injetável nos testes). `createCalcTool()` → Tool `calc` (aritmética via parser próprio restrito). Ambas seguem **puras**: sem `requirements`, sem rede/disco/efeito colateral, `calc` **não** usa `eval`/`Function`.
- `createReadFileTool({ fs? })` → Tool `read_file` (lê o conteúdo de um arquivo) e `createListDirTool({ fs? })` → Tool `list_dir` (lista as entradas de um diretório) — **primeiras Tools com IO** da plataforma. Cada uma declara `requirements(args) → ActionRequest` (o recurso e o `access: 'read'` que tocaria, como **dado**) e lê o disco pela porta injetável `FsReadPort` (`readFile`/`readdir`; default `nodeFsReadPort()` sobre `node:fs/promises`; fake nos testes — sem disco real). Erro de IO (arquivo/diretório ausente, `args` inválido) vira `ToolResult` de erro, nunca lança.
- `createWriteFileTool({ fs? })` → Tool `write_file` (cria ou **sobrescreve** um arquivo de texto; recebe `{ path, content }`) — **primeira Tool de escrita**. Declara `requirements(args) → ActionRequest` com `access: 'write'` e escreve pela porta injetável **separada** `FsWritePort` (default `nodeFsWritePort()` sobre `node:fs/promises`; fake nos testes). Não cria diretório-pai (resolvido por `mkdir`, SPEC-0013); `args` inválido ou erro de IO viram `ToolResult` de erro, nunca lança.
- `createDeleteFileTool({ fs? })` → Tool `delete_file` (remove um arquivo; recebe `{ path }`) — declara `access: 'delete'`, a única Tool que apaga dado existente de forma irreversível; por isso o Permission Service produz `confirm` (não `allowed` direto) e o Runtime pausa para perguntar antes de rodar (SPEC-0013, ADR-0013). `createMkdirTool({ fs? })` → Tool `mkdir` (cria diretório recursivamente, `{ recursive: true }`; recebe `{ path }`) e `createAppendFileTool({ fs? })` → Tool `append_file` (acrescenta conteúdo, criando o arquivo se ausente; recebe `{ path, content }`) — ambas declaram `access: 'write'` (não apagam nada existente, seguem `allowed`/`blocked` como `write_file`, sem confirmação).
- `FsWritePort` ganhou `deleteFile`/`mkdir`/`appendFile` (além de `writeFile`), todas sobre `node:fs/promises` no adapter default.
- Uma Tool **não decide permissão nem quando é usada** (Module Catalog) — `requirements` só descreve o recurso; quem julga é o Permission Service (`@atlas/permissions`) e quem aplica o veredicto (incluindo pausar para `confirm`) é o Runtime. A Tool só executa `run(args)` e devolve `ToolResult` estruturado (`ok`/`output`/`error`).
- Depende só de `@atlas/contracts` (Regra 5: Tools não dependem do Cognitive Core nem de `@atlas/permissions`). Contratos `Tool`/`ToolResult`/`ToolDescriptor`/`ToolRegistry`/`ActionRequest` vivem em `@atlas/contracts`; `FsReadPort` é interno ao package (sem 2º consumidor).
- **Fecho atômico de TOCTOU (SPEC-0017/ADR-0014):** `FsReadPort.readFile` e `FsWritePort.writeFile`/`appendFile` passam a executar, internamente, `open(path, flags | O_NOFOLLOW)` (o componente final não pode ser symlink no instante do uso) → ancoram a identidade do fd (`fstat`) contra a identidade do `realpath` (`stat`) — divergência = TOCTOU detectado, recusa — → aplicam um **verificador estreito injetado** `Verify = (realpath: string, access: AccessMode) => boolean` (tipo interno, sem 2º consumidor real, **não** sobe a `@atlas/contracts`, referenciando só `AccessMode`) → só então operam sobre o fd já verificado, e fecham sempre. Toda falha (symlink último hop, TOCTOU, fora da raiz no uso, IO) vira `ToolResult` de erro com mensagem distinta, propagada pelo `try/catch` já existente das Tools — **nunca lança**. `nodeFsReadPort`/`nodeFsWritePort` recebem `{ verify?, primitives? }`: **desde a SPEC-0024**, `verify` default é **fail-closed** (`() => false`) — uma porta construída sem `verify` injetado recusa `readFile`/`writeFile`/`appendFile` no instante do uso, em vez de permitir por omissão; `@atlas/core` fia o método novo do Permission Service (`isContained`) como `verify` real, então o comportamento em produção não muda (o default só é consultado por portas cruas/futuras, fora de `createAtlas`); `primitives` (`FsPrimitivesPort`, interno, default sobre `node:fs/promises`) existe só para permitir fakes nos testes (sem disco real), simulando `open` falhando (symlink) ou identidade divergente (TOCTOU). A porta **não conhece raízes nem o Permission Service** — só o predicado. `readdir`/`deleteFile`/`mkdir` **não mudam** (sem fecho atômico; residuais documentados no ADR-0014: troca de ancestral, `delete`/`mkdir`/`list_dir`, Windows).
- **Tools de git somente-leitura (SPEC-0028): `createGitStatusTool({ git?, cwd? })`, `createGitDiffTool({ git?, cwd? })`, `createGitLogTool({ git?, cwd? })`** — primeiras Tools da especialidade declarada do Atlas (desenvolvimento de software). Alvo é `args.path` (string não vazia) ou `cwd()` injetável (default `process.cwd`, mesmo alvo em `requirements` e `run`); `git_diff` aceita `staged?: boolean` (`--cached`); `git_log` aceita `maxCount?: number` (default **20**; valor inválido — não inteiro positivo — cai no default, sem erro). Todas declaram `requirements(args) → { resource: { type: 'directory', path }, access: 'read' }`; erro de IO vira `ToolResult` de erro, nunca lança; sucesso inclui o `repository` (toplevel real inspecionado) antes do texto do git no `output`, mesmo quando `path` foi omitido.
  - IO por `GitReadPort` interna (`status`/`diff`/`log`, sem 2º consumidor, não sobe a `@atlas/contracts` — mesmo critério de `FsReadPort`), adaptador default `nodeGitReadPort({ verify?, exec?, realpath? })` sobre `node:child_process` `execFile` (argv array, **nunca** `shell: true`). Para cada invocação: (1) descobre o **toplevel real** do repositório (`git --no-optional-locks -C <alvo> rev-parse --show-toplevel`, já que `status`/`diff`/`log` sobem pelos diretórios pais e relatariam — no `diff`, imprimiriam conteúdo de — toda a árvore acima de um alvo em subdiretório); (2) resolve o `realpath` desse toplevel (primitiva injetável, molde de `FsPrimitivesPort.realpath`, para permitir fake nos testes sem disco real); (3) aplica `verify(toplevel, 'read')` (mesmo `Verify` de `fs-port.ts`, reusado — **fail-closed por default**, `() => false`, SPEC-0024) — `false` recusa com `fora do diretório permitido: <toplevel>` e o subcomando **não roda**; (4) só então executa o subcomando **fixo** com `cwd` = toplevel verificado. `@atlas/core` fia `verify: permissions.isContained.bind(permissions)`, a mesma fiação já usada para `nodeFsReadPort`/`nodeFsWritePort`. Todo argv começa com `--no-optional-locks` (inclusive no `rev-parse`), para que a leitura não escreva no repositório (`git status` pode tomar lock no índice); subcomandos allowlistados (`rev-parse`/`status`/`diff`/`log`), nunca comando arbitrário. `maxBuffer` explícito de 10 MiB (estouro → `ToolResult` de erro estruturado); saída capturada truncada em 64 KiB com marcador visível e `truncated: true` — vale para os três, `git_diff` inclusive. A porta **não conhece raízes nem o Permission Service** — só o predicado `verify` injetado; a decisão de contenção continua só no Permission Service (ADR-0014).
  - **Residuais conhecidos (SPEC-0028, não fechados):** (1) sem fecho atômico de TOCTOU do diretório-alvo — quem lê é um **subprocesso** e o alvo é um **diretório**, não há fd a ancorar (mesmo critério com que o ADR-0014 deixou `list_dir` fora do fecho atômico); entre o `verify` do toplevel e o `execFile` do subcomando, o alvo pode em tese ser trocado por um symlink apontando para fora da raiz; (2) troca de ancestral — mesmo residual do ADR-0014 para `delete_file`/`mkdir`; (3) Windows fora de escopo (matriz de CI só-Linux, SPEC-0016); (4) `--no-optional-locks` evita as escritas opcionais, mas a configuração global do usuário (`~/.gitconfig`) segue sendo lida pelo git normalmente, fora do portão de `readRoots`; (5) a mensagem de recusa expõe um toplevel **descoberto** pelo `rev-parse` (não um path que o chamador já forneceu, como nas negações do `evaluate`) — revela a existência/localização de um repositório fora da raiz permitida (vazamento pequeno, com contrapartida de transparência do Artigo 7); o `rev-parse` também **lê configuração de git acima da raiz permitida** antes de qualquer veredicto ser aplicado.
