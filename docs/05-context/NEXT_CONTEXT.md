- **[SPEC-0028](../implementation/specs/SPEC-0028-git-read-only-tools.md) (Tools de git somente-leitura — `git_status`/`git_diff`/`git_log` em `@atlas/tools`): `Done`** (fechada em 2026-07-22, Perfil `completo` — `spec-validator` separado deu o veredicto "pronta", `architecture-reviewer` vetou a 1ª versão da SPEC no gate (1 rodada, sem escalação); o `spec-closer` só fechou). Item **1.4 (Capacidades de Plataforma)** do Roadmap, l. 100, `candidato · SPEC direta`, marcado **parcialmente entregue** (1ª das três fatias nomeadas nesse item; **não** fecha nenhum gate — o único gate de 1.4, Skills, já fechado pela SPEC-0025). As **primeiras Tools da especialidade declarada do Atlas** (desenvolvimento de software) — até aqui só existiam Tools genéricas de filesystem. `@atlas/tools` ganha `createGitStatusTool({ git?, cwd? })`/`createGitDiffTool({ git?, cwd? })`/`createGitLogTool({ git?, cwd? })`, todas declarando `requirements(args) → { resource: { type: 'directory', path }, access: 'read' }` (reusa `AccessMode`/`ResourceType` já existentes, **diff vazio em `@atlas/contracts`**) e chamando a porta interna `GitReadPort` (`status`/`diff`/`log`), adaptador default `nodeGitReadPort({ verify?, exec?, realpath? })` sobre `node:child_process` `execFile` (argv array, nunca `shell: true`). **Achado central do gate (bloqueante A)**: `git status`/`diff`/`log` **descobrem o repositório subindo pelos diretórios pais** — diferente de `list_dir`, que nunca lê acima do path declarado; a 1ª versão da SPEC afirmava requisitos "idênticos a `list_dir`", premissa falsa. Correção: a porta descobre o **toplevel real** (`git --no-optional-locks -C <alvo> rev-parse --show-toplevel`) → resolve `realpath` → aplica `verify(toplevel, 'read')` (mesmo `Verify` estreito de `fs-port.ts`, fail-closed por default, SPEC-0024) **antes** de qualquer subcomando — toplevel fora das `readRoots` → recusa estruturada (o subcomando não roda), asseverado por spy (exatamente 1 chamada de `exec`, a de `rev-parse`). `@atlas/core` fia `verify: permissions.isContained.bind(permissions)` — mesma fiação já usada para `nodeFsReadPort`/`nodeFsWritePort`, **nenhuma config nova**. **Bloqueante C**: `git status` pode atualizar `.git/index`/tomar lock — escrita real sob veredicto `read` com `writeRoots` vazio por default; resolvido com `--no-optional-locks` obrigatório em todo argv (inclusive no `rev-parse`), asseverado nos três métodos, em vez de promover `git_status` a `access: 'write'`. `execFile` com `maxBuffer` explícito (10 MiB, estouro → erro estruturado) e saída truncada em 64 KiB com marcador + `truncated: true` (vale para os três, `git_diff` inclusive — o pior caso). `GitOutput.repository` (toplevel real) no `output` de sucesso antes do texto do git, mesmo com `path` ausente (Artigo 7). `git_diff` aceita `staged?: boolean`; `git_log` aceita `maxCount?: number` (default **20**, valor inválido cai no default sem erro — allowlist bounded que mantém a fatia fora do território `ADR primeiro` de "execução de comandos", mesmo item do Roadmap). Saída em texto cru, sem parsing estruturado (molde `read_file`). **Residuais documentados, não fechados** (mesmo critério do ADR-0014 para `list_dir`): sem fecho atômico de TOCTOU do diretório-alvo (subprocesso sobre diretório, sem fd a ancorar), troca de ancestral, Windows fora de escopo, `~/.gitconfig` lido fora do portão, mensagem de recusa expõe um toplevel **descoberto** (vazamento pequeno com contrapartida de transparência) — candidato natural de reuso na fatia futura de "leitura de estrutura de projeto" (observação do `architecture-reviewer`). **Diff vazio** em `@atlas/permissions`/`@atlas/runtime` também. Fora de escopo (mesmo item do Roadmap): mutação do repositório, execução de comandos arbitrários (novo `access`, `ADR primeiro`), leitura de estrutura de projeto, contexto de ambiente (ADR-0009). Atrito de implementação: recorrência do padrão `exactOptionalPropertyTypes` já registrado na SPEC-0020 (`opts ?? {}` nos fakes de `git-diff`/`git-log`); 3 desvios pequenos dos "Arquivos Esperados", todos aceitos pelo validator (`realpath?` injetável, `CreateAtlasDeps.git?`, teste de wiring manual — precedentes já existentes no repo). **membro obrigatório novo numa _interface de contrato_** (não numa `Deps` de factory — ex.: `PermissionService.isContained`, SPEC-0017) não é pego pelo grep-por-construtor: a busca certa é pelo **nome do tipo** (`git grep 'PermissionService'`), que acha os fakes/implementações diretas do tipo em testes — foi exatamente o que quebrou o typecheck de `runtime.test.ts` na SPEC-0017; **`vitest run` não faz typecheck** (esbuild só remove tipos) — um passo de TDD "RED" que depende de um erro de *tipo* (campo `Deps` novo obrigatório, assinatura mudada) só falha de verdade rodando `pnpm --filter <pkg> typecheck`, nunca confie em `vitest run` sozinho para confirmar essa falha.

# Avisos Operacionais (deste ambiente)

- `pnpm add` na raiz do workspace exige a flag `-w`.
- **pnpm 11 não lê mais o campo `pnpm` do `package.json`**: aprovar build de dependências (ex.: `esbuild`, motor do `tsx`) vive em `pnpm-workspace.yaml` (`allowBuilds: { esbuild: true }`). Sem isso, `pnpm install` sai com código 1 (`ERR_PNPM_IGNORED_BUILDS`) e trava scripts do pnpm.
- **Node nativo não roda o fonte**: a convenção de imports `.js` (NodeNext) do repo não é remapeada pelo _type stripping_ do Node; por isso apps rodam via `tsx` (ADR-0005). Ao rodar TS diretamente, use `tsx`, não `node`.
- O proxy de output (RTK) mascara saída/erros; para ver o completo, `rtk proxy <cmd>`; log em `~/Library/Application Support/rtk/tee/`.
- O executor de comandos do harness pode ficar indisponível temporariamente; o usuário pode rodar comandos com o prefixo `!` para destravar verificações.
- Prettier ignora `**/*.md` por design (protege a documentação manuscrita); commits terminam com o trailer `Co-Authored-By` do modelo em uso.
